# Vision de producto

## Vision

Horarios SENA busca convertirse en una base organizada para gestionar informacion academica relacionada con programas, fichas, actores, ambientes, horarios, proyectos formativos y eventos de coordinacion.

La vision inicial no es construir software de inmediato, sino dejar claro que debe existir, por que debe existir y como debe documentarse para que el equipo pueda implementarlo despues con menos ambiguedad.

## Problema que atiende

El equipo necesita una forma clara de entender y conectar:

- Estructura institucional.
- Catalogos y parametros.
- Ambientes e inventario.
- Programas, competencias y RAP.
- Fichas, proyectos formativos y entregables.
- Instructores, aprendices y directivos.
- Horarios, incidencias y observaciones.
- Seguimiento, KPIs, notificaciones y eventos.

Cuando estos elementos se documentan separados o con nombres confusos, el proyecto pierde trazabilidad.

## Propuesta de valor

- Dar una lectura unica del proyecto.
- Facilitar que los companeros sepan donde documentar cada cosa.
- Preparar la arquitectura para crecer sin inventar microservicios antes de tiempo.
- Mantener trazabilidad entre requisitos, dominio, arquitectura, APIs y servicios.
- Evitar documentos vacios, repetidos o dificiles de entender.

## Usuarios beneficiados

| Usuario o grupo | Beneficio |
|-----------------|-----------|
| Equipo de documentacion | Sabe que estructura seguir y que debe completar |
| Arquitectura | Tiene limites funcionales y trazabilidad para tomar decisiones |
| Desarrollo futuro | Recibe requisitos y modulos mejor definidos |
| QA o revision | Puede validar documentos contra criterios claros |
| Usuarios academicos | Podran entender manuales y flujos cuando se documenten |

## Principio de producto

Primero claridad documental, despues implementacion. Si el equipo no puede explicar un modulo, requisito o servicio en Markdown, todavia no deberia convertirlo en codigo.
